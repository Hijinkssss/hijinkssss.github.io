# Maintaining public content

`assets/js/site-data.js` is the single content source. It is ordinary JavaScript loaded before `site.js`; it works on static hosting and local `file:` previews without fetching JSON. Keep strings plain text. The renderer escapes them.

## Add a released project

Duplicate an existing entry in `projects`. Assign a unique lowercase `id` such as `new-mod`. Required fields:

| Field | Meaning |
|---|---|
| `id`, `code`, `name`, `category` | URL identifier, short label, display name, category |
| `version`, `date`, `status` | Packaged version, publication date in `YYYY-MM-DD`, release status |
| `tagline`, `description` | Short project copy |
| `image`, `imageAlt` | Relative local image path and meaningful alternative text |
| `repo`, `release`, `download`, `filename` | Public source, exact release, packaged asset URL, matching filename |
| `nexus`, `upstreamDocs` | Public Nexus listing and complete documentation; null suppresses an optional link |
| `features`, `install`, `limitations` | Arrays of plain text |
| `requirements`, `compatibility`, `usage` | Plain text scoped to this specific version |
| `faq` | Array of `{ question, answer }` |
| `media` | Array of `{ src, alt, caption, type }` |

Project cards, detail pages, manual sections, and download buttons render from the same object. If you add a category, add its filter button to `index.html`; the catalog count updates automatically. Add a release filter button in `changelog.html` for a new project. No file per project is needed.

Only add a project to this public file when it is ready to be public. Hiding an entry with CSS does not keep its source private.

## Update a release

1. Update the project's `version`, `date`, `release`, `download`, and `filename` together.
2. Update requirements, compatibility, screenshots, and project copy if behavior changed.
3. Add a new object to `updates` with the project `id`, version, date, title, short notes, and exact release URL. Keep it in newest-first order. Do not erase older notes unless they are incorrect.
4. Update `checkedOn` and the visible verification dates in `index.html` and `changelog.html`.
5. Verify every primary download resolves to the packaged ZIP, rather than GitHub's autogenerated source archive.

The shared FAA repository may eventually hold multiple projects. Using its generic `/releases/latest` URL can route users to the wrong project's release. Exact release/asset URLs are used here intentionally. For a dedicated one-project repository, `/releases/latest` is an optional landing page, but still verify that the version and download filename agree.

## Add screenshots or video

Put screenshot files in `assets/images/`. Add entries to a project's `media` array with a relative path, alternative text, honest caption, and `type: 'Gameplay screenshot'`. The first item should be the main project artwork: the detail hero opens media index 0. Every image receives a working enlargement button.

For a gameplay video, add a normal external video link in a project description section, or extend the media renderer with native `<video controls preload="metadata">` and a local file. No autoplay or fake play button is included. Project artwork is explicitly labeled and is not presented as a gameplay screenshot.

## Steam guides

Add `{ title, subtitle, label, icon, description, url }` objects to `guides`. Supported decorative icon choices are `target` and `bolt`; the guide copy and link are independent of the icon. Keep the public Steam guide separate from any unreleased project with a similar name.

## Before publishing

Open the homepage, both project pages, manual, and changelog. Try a search with no results, filter each category, follow the project install links, expand media, and inspect a phone-width layout. Keep private drafts outside the repository. The GitHub Actions upload allowlist adds another boundary, but source committed to a public repository is still public.
